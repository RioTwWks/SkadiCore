# Протоколы SkadiCore

Документ описывает, какие протоколы поддерживаются, в каком объёме,
какие у них ограничения и как их отлаживать вручную.

**Важно**: этот документ описывает **текущее состояние** кода, а не
спецификации RFC. Если реализация расходится со спецификацией — здесь
написано, как именно.

## Общие принципы

Все протоколы в SkadiCore следуют одним и тем же правилам:

1. **Парсеры — чистые функции.** Разбор байтов вынесен в модули
   `parse.rs` без I/O. Это позволяет фаззить их отдельно.
2. **Лимиты на всё.** Максимальные длины полей заданы константами
   в коде. Превышение — ошибка, а не попытка аллоцировать больше.
3. **Таймаут на handshake.** Вся фаза переговоров ограничена
   10 секундами (`NEGOTIATION_TIMEOUT` / `HANDSHAKE_TIMEOUT`).
4. **Константное сравнение секретов.** Пароли и UUID сравниваются
   через `subtle::ConstantTimeEq`.
5. **Молчаливое закрытие при ошибке аутентификации** (для VLESS)
   или минимальный reply (для SOCKS5).

## SOCKS5

Реализация: `crates/skadi-protocol/src/socks5/`.

Спецификации:
- [RFC 1928](https://datatracker.ietf.org/doc/html/rfc1928) — SOCKS5
- [RFC 1929](https://datatracker.ietf.org/doc/html/rfc1929) — user/pass auth

### Что поддерживается

| Функция | Статус |
|---|---|
| Версия протокола | 0x05 |
| Метод no-auth | ✅ |
| Метод user/pass | ✅ |
| Команда CONNECT | ✅ |
| Команда BIND | ❌ |
| Команда UDP ASSOCIATE | ❌ |
| ATYP IPv4 | ✅ |
| ATYP Domain | ✅ |
| ATYP IPv6 | ✅ |

### Greeting

Клиент присылает:

```
+-----+----------+----------+
| VER | NMETHODS | METHODS  |
+-----+----------+----------+
|  1  |    1     | 1 to 255 |
+-----+----------+----------+
```

**Ограничения SkadiCore**:
- `NMETHODS` не может быть 0.
- `NMETHODS` не может превышать **16** (`MAX_METHODS`).
  RFC допускает до 255, но на практике методов 1–3.
- `VER` должен быть `0x05`.

Сервер отвечает двумя байтами:

```
+-----+--------+
| VER | METHOD |
+-----+--------+
|  1  |   1    |
+-----+--------+
```

`METHOD` — выбранный метод:
- `0x00` — no-auth
- `0x02` — user/pass
- `0xFF` — нет приемлемого метода (соединение закрывается)

### Аутентификация (RFC 1929)

Если выбран `0x02`, клиент присылает:

```
+-----+------+----------+------+----------+
| VER | ULEN |  UNAME   | PLEN |  PASSWD  |
+-----+------+----------+------+----------+
|  1  |  1   | 1 to 255 |  1   | 1 to 255 |
+-----+------+----------+------+----------+
```

**Ограничения SkadiCore**:
- `VER` должен быть `0x01`.
- `ULEN` не может быть 0.
- `PLEN` не может быть 0.
- `UNAME` и `PASSWD` должны быть валидным UTF-8.

Сервер отвечает:

```
+-----+--------+
| VER | STATUS |
+-----+--------+
|  1  |   1    |
+-----+--------+
```

`STATUS`:
- `0x00` — успех
- `0x01` — провал (соединение закрывается)

**Защита от timing-атак**: при неизвестном логине сервер
сравнивает пароль с заглушкой `__no_such_user__`, чтобы время
ответа не выдавало существование пользователя.

### Запрос

После успешной аутентификации клиент присылает:

```
+-----+-----+-------+------+----------+----------+
| VER | CMD |  RSV  | ATYP | DST.ADDR | DST.PORT |
+-----+-----+-------+------+----------+----------+
|  1  |  1  | X'00' |  1   | Variable |    2     |
+-----+-----+-------+------+----------+----------+
```

**Ограничения SkadiCore**:
- `VER` должен быть `0x05`.
- `CMD` должен быть `0x01` (CONNECT). Остальные команды
  отвергаются с reply `0x07` (command not supported).
- `RSV` должен быть `0x00`. Иначе — ошибка.
- `ATYP` может быть `0x01` (IPv4), `0x03` (Domain), `0x04` (IPv6).

**Длина адреса**:
- IPv4: 4 байта.
- IPv6: 16 байт.
- Domain: 1 байт длины + до 255 байт имени. Пустая строка
  отвергается.

### Reply

Сервер отвечает:

```
+-----+-----+-------+------+----------+----------+
| VER | REP |  RSV  | ATYP | BND.ADDR | BND.PORT |
+-----+-----+-------+------+----------+----------+
|  1  |  1  | X'00' |  1   | Variable |    2     |
+-----+-----+-------+------+----------+----------+
```

`REP` — код ответа:

| Код | Значение | Когда отправляется |
|---|---|---|
| `0x00` | succeeded | Upstream установлен |
| `0x01` | general failure | Прочие ошибки |
| `0x02` | not allowed | (не используется) |
| `0x03` | network unreachable | (не используется) |
| `0x04` | host unreachable | Connect timeout |
| `0x05` | connection refused | Upstream отверг |
| `0x06` | TTL expired | (не используется) |
| `0x07` | command not supported | CMD != 0x01 |
| `0x08` | address type not supported | Неизвестный ATYP |

`BND.ADDR` и `BND.PORT` — адрес, с которого сервер подключился
к цели. При успехе — реальный `local_addr()` upstream-сокета.
При ошибке — `0.0.0.0:0`.

### Пример: no-auth CONNECT к example.com:443

**Клиент → сервер (greeting)**:
```
05 01 00
│  │  └─ метод: no-auth
│  └──── количество методов: 1
└─────── версия: 5
```

**Сервер → клиент (выбор метода)**:
```
05 00
│  └─ выбран no-auth
└──── версия: 5
```

**Клиент → сервер (запрос)**:
```
05 01 00 03 0B 65 78 61 6D 70 6C 65 2E 63 6F 6D 01 BB
│  │  │  │  │  └─────────── "example.com" ──────────┘ └─ порт 443
│  │  │  │  └─ длина домена: 11
│  │  │  └─ ATYP: domain
│  │  └─ RSV: 0
│  └─ CMD: CONNECT
└─ версия: 5
```

**Сервер → клиент (успех)**:
```
05 00 00 01 5F 1A 2B 3C 1F 90
│  │  │  │  └─────── BND.ADDR: 95.26.43.60 ──────┘ └─ BND.PORT: 8080
│  │  │  └─ ATYP: IPv4
│  │  └─ RSV: 0
│  └─ REP: succeeded
└─ версия: 5
```

После этого начинается релей байтов в обе стороны.

### Что НЕ реализовано

- **BIND** — команда для входящих соединений. Редко используется
  в прокси-сценариях.
- **UDP ASSOCIATE** — UDP-релей. Нужен для QUIC, DNS-over-UDP,
  игр. Сложен в реализации, отложен.
- **GSSAPI** — метод аутентификации `0x01`. Не нужен.

## VLESS

Реализация: `crates/skadi-protocol/src/vless/`.

VLESS не имеет формальной RFC. Референс — реализация в
[Xray-core](https://github.com/XTLS/Xray-core). Документ описывает
поведение SkadiCore, которое совместимо с Xray для базового случая.

### Что поддерживается

| Функция | Статус |
|---|---|
| Версия протокола | 0x00 |
| UUID-аутентификация | ✅ |
| Команда TCP | ✅ |
| Команда UDP | ✅ |
| Команда Mux | ✅ (TCP + UDP) |
| Addons (чтение) | ✅ |
| Addons (интерпретация) | ✅ (flow/seed) |
| Flow `xtls-rprx-vision` | ❌ (явный reject) |
| ATYP IPv4 | ✅ |
| ATYP Domain | ✅ |
| ATYP IPv6 | ✅ |
| Ответный заголовок | ✅ |

### Заголовок запроса

Клиент присылает:

```
+-----+------+----------+---------+---------+---------+----------+
| VER | UUID | ADDONS_L | ADDONS  | COMMAND |  PORT   |   ATYP   |
+-----+------+----------+---------+---------+---------+----------+
|  1  |  16  |    1     | 0 to M  |    1    |    2    |    1     |
+-----+------+----------+---------+---------+---------+----------+
```

Затем идёт адрес в зависимости от `ATYP`, затем — полезная
нагрузка (первые байты данных).

**Ограничения SkadiCore**:
- `VER` должен быть `0x00`. Другие версии отвергаются.
- `ADDONS_L` не может превышать **512** байт (`MAX_ADDONS`).
  Xray на практике использует 0–2 байта.
- `COMMAND` может быть `0x01` (TCP), `0x02` (UDP) или `0x03` (Mux).
  Для Mux поля `PORT`/`ATYP`/`ADDR` **не передаются** — после команды
  сразу идут Mux-кадры.
- `ATYP` может быть `0x01` (IPv4), `0x02` (Domain), `0x03`
  (IPv6). **Внимание**: в SOCKS5 домен — `0x03`, в VLESS —
  `0x02`. Классическая ловушка.
- Длина домена — до 255 байт. Пустая строка отвергается.

### Порядок полей: важное отличие от SOCKS5

В SOCKS5 порядок такой: `ATYP → ADDR → PORT`.
В VLESS порядок такой: `PORT → ATYP → ADDR`.

Это не ошибка. Спецификация VLESS размещает порт перед адресом.
При написании парсера легко перепутать.

### Addons

Поле `ADDONS` — это Protobuf-сообщение. В базовом VLESS оно
пустое (длина 0). Xray использует его для:

- `flow` — например, `xtls-rprx-vision`;
- `seed` — для Vision-совместимости.

SkadiCore **читает и интерпретирует** addons: извлекает `flow` и
`seed`. Flow `xtls-rprx-vision` и любой другой непустой flow
**отвергаются** — соединение закрывается без ответного заголовка
(как при неверном UUID). Клиенты без flow (пустые addons) работают
как раньше.

### Ответный заголовок

Сервер отвечает **всегда двумя байтами**:

```
+-----+----------+
| VER | ADDONS_L |
+-----+----------+
|  1  |    1     |
+-----+----------+
```

`VER` — копия версии из запроса (всегда `0x00`).
`ADDONS_L` — всегда `0x00` (у SkadiCore нет addons в ответе).

В отличие от SOCKS5, в ответе **нет bound-адреса**. Клиент не
узнаёт, с какого адреса сервер подключился к цели. Это осознанное
упрощение VLESS.

### Аутентификация

UUID из заголовка сравнивается со списком в конфиге. Сравнение —
за постоянное время через `subtle::ConstantTimeEq`.

**Критично**: при неверном UUID сервер **не отправляет ничего**.
Соединение просто закрывается. Это требование спецификации:
активный зонд не должен отличить прокси от закрытого порта.

В логах это выглядит так:

```json
{"level":"WARN","message":"VLESS auth failed, closing silently","uuid":"..."}
```

`uuid` логируется в hex-форме. Это допустимо: UUID — это
идентификатор, а не секрет в строгом смысле. Но если паранойя
требует — можно заменить на хеш.

### Пример: TCP CONNECT к example.com:443

**Клиент → сервер**:
```
00
B8 31 38 1D 63 24 4D 53 AD 4F 8C DA 48 B3 08 11
00
01
01 BB
02
0B
65 78 61 6D 70 6C 65 2E 63 6F 6D
[первые байты TLS ClientHello...]
```

Разбор:
```
00                          — версия VLESS
B8 31 ... 08 11             — UUID (16 байт)
00                          — длина addons: 0
01                          — команда: TCP
01 BB                       — порт: 443
02                          — ATYP: domain
0B                          — длина домена: 11
65 78 ... 6F 6D             — "example.com"
...                         — полезная нагрузка
```

**Сервер → клиент (ответный заголовок)**:
```
00 00
│  └─ addons length: 0
└──── версия: 0
```

После этого начинается релей байтов в обе стороны.

### Что НЕ реализовано

- **XUDP.** Реализованы XUDP New/Keep кадры с `session_id=0`,
  8-byte `GlobalID` и per-packet UDP-адресацией. GlobalID hit/reconnect
  (Xray `XUDPManager`): реестр cone-сокетов, TTL 60s, abort reader при hit.
- **Flow `xtls-rprx-vision`.** Парсится из addons, но явно
  отвергается. Клиенты, требующие Vision, не подключатся.
- **Response addons.** Сервер всегда отвечает с `ADDONS_L = 0`.

### UDP over VLESS

После handshake данные идут length-prefixed кадрами: `2-byte BE
length + payload` в обе стороны (как в Xray-core). Один TCP/VLESS
сеанс = один UDP-поток к целевому `host:port`.

## Сравнение

| Аспект | SOCKS5 | VLESS |
|---|---|---|
| Аутентификация | Логин/пароль | UUID |
| Порядок полей запроса | ATYP → ADDR → PORT | PORT → ATYP → ADDR |
| ATYP для домена | 0x03 | 0x02 |
| Bound-адрес в ответе | Есть | Нет |
| Размер ответа | Variable (10–22 байта) | 2 байта |
| Ответ при ошибке auth | `VER, 0x01` | Молчание |
| Расширяемость | Нет | Addons (Protobuf) |
| Flow | Нет | Есть (не поддержан) |

## Диагностика

### Как понять, что сервер получил запрос

Запустите с `--log-level debug`. В логах появится:

**SOCKS5**:
```json
{"level":"DEBUG","message":"SOCKS5 CONNECT request","target":"example.com:443"}
```

**VLESS**:
```json
{"level":"DEBUG","message":"VLESS request decoded","command":1,"addons_len":0,"target":"example.com:443"}
```

Если этих строк нет — handshake не дошёл до конца. Проверьте:
- Клиент действительно использует этот протокол?
- Порт не занят другим сервисом?
- Файрвол не режет соединение?

### Как поймать байты

Для ручной отладки используйте `socat` или `nc`:

```bash
# Слушать на порту и печатать hex
socat -v TCP-LISTEN:1080,reuseaddr,fork -
```

Или `tcpdump`:

```bash
sudo tcpdump -i lo -X 'tcp port 1080'
```

### Типичные ошибки

**SOCKS5: `no acceptable auth method`**
Клиент предлагает методы, которые не совпадают с конфигом.
Например, сервер настроен на `user-pass`, а клиент шлёт только
`no-auth`.

**SOCKS5: `authentication failed`**
Неверный логин или пароль. Проверьте конфиг:
```toml
[[protocol.socks5.users]]
username = "alice"
password = "change-me"
```

**VLESS: `authentication failed`**
UUID не найден в конфиге. Проверьте формат: 32 hex-цифры,
опционально с дефисами. Регистр не важен.

**VLESS: `VLESS handshake timeout`**
Клиент подключился, но не прислал заголовок за 10 секунд.
Возможно, клиент использует TLS, а сервер ждёт plain TCP
(или наоборот).

**`unsupported address type: 0xXX`**
Клиент прислал ATYP, который SkadiCore не поддерживает.
Например, для VLESS `0x04` (не существует) или для SOCKS5
`0x02` (устаревший).

**`addons too large`**
VLESS-клиент прислал addons больше 512 байт. Это
нестандартно. Проверьте настройки клиента.

### Проверка с curl

SOCKS5:
```bash
curl -x socks5h://127.0.0.1:1080 https://example.com -v
```

С аутентификацией:
```bash
curl -x socks5h://alice:change-me@127.0.0.1:1080 https://example.com -v
```

`-x socks5h` (а не `socks5`) означает, что DNS-резолвинг
происходит на стороне прокси. Для обхода блокировок это
правильный выбор: иначе DNS-запрос уходит провайдеру и
утекает.
