## Обзор

SkadiCore — это **серверное ядро** для обхода блокировок. Оно:

1. Слушает входящие соединения на заданном порту.
2. Определяет, какой протокол использовать (SOCKS5, VLESS).
3. Проводит handshake: аутентифицирует пользователя, извлекает
   целевой адрес.
4. Устанавливает исходящее соединение с целевым адресом.
5. Релеит байты в обе стороны до закрытия.

Всё остальное — TLS-обёртка, маскировка, метрики, управление
пользователями — надстраивается вокруг этого ядра.

## Структура workspace

```
skadicore/
├── Cargo.toml              # workspace root
├── rust-toolchain.toml     # фиксация версии Rust
├── rustfmt.toml            # стиль форматирования
├── README.md
├── SECURITY.md
├── docs/
│   ├── ARCHITECTURE.md     # этот файл
│   └── PROTOCOLS.md        # детали SOCKS5 и VLESS
├── config/
│   └── skadi.toml
└── crates/
    ├── skadi-core/         # типы, трейты, ошибки
    ├── skadi-transport/    # TCP, позже TLS и XHTTP
    ├── skadi-protocol/     # SOCKS5, VLESS, позже REALITY
    │   └── fuzz/           # fuzz-таргеты (отдельный workspace)
    └── skadi-server/       # бинарник + lib (тесты)
        └── tests/          # TLS e2e (SOCKS5, VLESS, SNI)
```

### Почему workspace, а не один крейт

- **Изоляция тестов.** Fuzz-тесты требуют nightly и отдельного
  профиля сборки. Держать их в основном workspace нельзя.
- **Явные границы.** Если `skadi-core` начнёт зависеть от
  `tokio::net`, это сразу видно в `Cargo.toml` и можно
  остановить.
- **Параллельная сборка.** Cargo компилирует крейты параллельно,
  что ускоряет инкрементальные сборки.
- **Переиспользование.** `skadi-core` и `skadi-protocol` можно
  будет использовать в клиенте, не таща за собой серверный код.

## Слои и зависимости

```
┌──────────────────────────────────────────┐
│           skadi-server (bin)             │
│  main, config, accept loop, handle_client│
└────────────┬─────────────┬───────────────┘
             │             │
             ▼             ▼
┌──────────────────┐  ┌────────────────────┐
│  skadi-transport │  │  skadi-protocol    │
│  TcpTransport    │  │  SOCKS5, VLESS     │
└────────┬─────────┘  └─────────┬──────────┘
         │                      │
         └──────────┬───────────┘
                    ▼
         ┌──────────────────────┐
         │      skadi-core      │
         │  Endpoint, Session,  │
         │  Error, UserId       │
         └──────────────────────┘
```

### Правила зависимостей

- **`skadi-core`** не зависит ни от чего, кроме `thiserror`,
  `serde`, `tracing`. Никакого `tokio::net`, никакой логики
  протоколов.
- **`skadi-transport`** зависит от `skadi-core` и `tokio`. Не
  знает про SOCKS5 или VLESS.
- **`skadi-protocol`** зависит от `skadi-core` и `tokio`. Парсит
  байты, но I/O делает через переданный `TcpStream`.
- **`skadi-server`** зависит от всех трёх. Связывает их вместе.

Нарушение этих правил — сигнал, что архитектура поплыла.

## Поток обработки соединения

```
                    ┌───────────────────┐
                    │  TcpListener      │
                    │  accept()         │
                    └─────────┬─────────┘
                              │
                              ▼
                    ┌───────────────────┐
                    │  tokio::spawn     │
                    │  handle_client()  │
                    └─────────┬─────────┘
                              │
              ┌───────────────┴───────────────┐
              ▼                               ▼
    ┌──────────────────┐            ┌──────────────────┐
    │ VLESS handshake  │            │ SOCKS5 negotiate │
    │ (если enabled)   │            │ (если enabled)   │
    └────────┬─────────┘            └─────────┬────────┘
             │                                │
             │ Endpoint                       │ Endpoint
             └───────────────┬────────────────┘
                             ▼
                   ┌───────────────────┐
                   │ TcpTransport      │
                   │ ::connect()       │
                   └─────────┬─────────┘
                             │
              ┌──────────────┴──────────────┐
              ▼                             ▼
     (VLESS: ответ уже             (SOCKS5: send_reply
      отправлен в handshake)        с bound-адресом)
              │                             │
              └──────────────┬──────────────┘
                             ▼
                   ┌───────────────────┐
                   │ copy_bidirectional│
                   │ (релей в обе      │
                   │  стороны)         │
                   └─────────┬─────────┘
                             │
                             ▼
                   ┌───────────────────┐
                   │  Session closed   │
                   │  метрики, логи    │
                   └───────────────────┘
```

### Асимметрия VLESS и SOCKS5

Ключевое отличие: **SOCKS5 отправляет reply после установки
upstream-соединения**, а **VLESS отправляет ответный заголовок
сразу после аутентификации**.

- **SOCKS5**: reply содержит bound-адрес (адрес, с которого
  сервер подключился к цели). Клиент может его использовать для
  NAT-траверса. Поэтому reply идёт после `connect()`.
- **VLESS**: ответный заголовок — 2 байта (версия + 0 addons).
  Адреса в нём нет. Поэтому его можно отправить сразу.

Это влияет на `handle_client`: для VLESS `handshake` возвращает
`Endpoint` и сам пишет ответ; для SOCKS5 `negotiate` возвращает
`Endpoint`, а `send_reply` вызывается отдельно. Если будете
добавлять третий протокол — решите, к какой модели он ближе,
и не пытайтесь унифицировать их преждевременно.

## Жизненный цикл сессии

Каждое соединение проходит через состояния:

```
   Created
      │
      │ Session::new(peer)
      ▼
  Negotiating ──── ошибка ────► Failed
      │
      │ Endpoint получен
      ▼
  Connecting ───── ошибка ────► Failed (с reply)
      │
      │ upstream установлен
      ▼
   Relaying
      │
      │ EOF / RST / таймаут
      ▼
   Closed
```

### Что происходит в каждом состоянии

- **Created.** `Session` создан, `SessionId` присвоен. Логируется
  peer-адрес.
- **Negotiating.** Выполняется handshake протокола. Здесь
  возможны таймауты (10 секунд по умолчанию) и ошибки парсинга.
- **Connecting.** Устанавливается соединение с целевым адресом.
  Таймаут подключения — 10 секунд.
- **Relaying.** `copy_bidirectional` гоняет байты. Здесь нет
  парсинга — только копирование.
- **Closed.** Логируется количество переданных байт, сессия
  удаляется из активных.

### Почему нет явной state machine

На MVP это было бы избыточно. Но когда появятся метрики и gRPC
API, состояние сессии понадобится для:
- ответа на `ListSessions()` (какие сессии активны);
- диагностики (`почему эта сессия висит в Negotiating?`);
- отмены по требованию администратора.

Тогда имеет смысл добавить enum `SessionState` и хранить сессии
в `DashMap<SessionId, Arc<SessionHandle>>`.

## Принятые решения

### 1. Парсеры — чистые функции

**Решение**: весь разбор недоверенных данных вынесен в модули
`parse.rs` без I/O. Функции принимают `&[u8]` и возвращают
`Result<(T, usize), ParseError>`.

**Почему**:
- **Fuzz-тестирование.** Fuzzer работает с байтами, а не с
  сокетами. Без чистых функций пришлось бы мокать `TcpStream`.
- **Юнит-тесты без сети.** Парсер проверяется за микросекунды.
- **Переиспользование.** Тот же парсер можно использовать на
  клиенте для отладки.
- **Понятность.** Легко доказать, что парсер не делает ничего
  кроме чтения байтов.

**Цена**: I/O-обвязка становится чуть сложнее — нужно правильно
дочитать нужное количество байт. Но это плата за тестируемость.

### 2. Таймаут на всю фазу переговоров

**Решение**: `VlessHandler::handshake` и
`Socks5Handler::negotiate` оборачивают свою работу в
`tokio::time::timeout(NEGOTIATION_TIMEOUT, ...)`.

**Почему**:
- Защита от **Slowloris**: клиент может открыть соединение и
  медленно присылать байты, занимая ресурсы.
- Простая альтернатива пер-операционным таймаутам, которые
  сложнее в реализации и настройке.

**Цена**: медленные, но легитимные клиенты (мобильный интернет,
спутник) могут отваливаться. 10 секунд — компромисс. Если
понадобится, таймаут станет настраиваемым.

### 3. Константное сравнение секретов

**Решение**: пароли и UUID сравниваются через
`subtle::ConstantTimeEq`.

**Почему**:
- **Timing-атаки.** Обычное `==` для строк возвращается на
  первом несовпадающем байте. По времени ответа можно узнать,
  сколько байт совпало, и перебрать секрет по частям.
- **Утечка существования пользователя.** Если неверный логин
  обрабатывается быстрее, чем неверный пароль, это выдаёт
  существование логина.

**Детали**:
- В SOCKS5 при неизвестном логине сравниваем с заглушкой
  `__no_such_user__`, чтобы время было одинаковым.
- В VLESS сравниваем все UUID в списке без early-return —
  иначе время ответа зависит от позиции пользователя в списке.

**Что не защищено**: длина сравниваемых строк. Для SOCKS5 длина
пароля не считается секретом (RFC его передаёт открытым в
заголовке). Для UUID длина фиксирована.

### 4. Молчаливое закрытие при ошибке аутентификации VLESS

**Решение**: если UUID не найден, `VlessHandler` просто
возвращает ошибку, не отправляя ничего клиенту. `handle_client`
закрывает соединение.

**Почему**:
- **Активное зондирование.** Если сервер отвечает по-разному на
  валидный и невалидный UUID, DPI может отличить прокси от
  закрытого порта.
- **Спецификация VLESS** прямо предписывает такое поведение.

**Детали**: `handle_client` при ошибке handshake логирует её, но
не пытается отправить что-либо в сокет. Соединение закрывается
через `Drop`.

### 5. `TcpTransport` не знает про протоколы

**Решение**: `TcpTransport::connect(endpoint)` принимает
`Endpoint` и возвращает `TcpStream`. Никаких хинтов про
VLESS/SOCKS5.

**Почему**:
- **Разделение ответственности.** Транспорт отвечает за
  соединение, протокол — за семантику.
- **Тестируемость.** `TcpTransport` можно протестировать на
  любых endpoint'ах без протокольного контекста.
- **Будущие транспорты.** Когда появится XHTTP или TLS,
  `TcpTransport` останется базовым слоем, а новые транспорты
  будут оборачивать его.

**Что в нём уже есть**:
- `TCP_NODELAY` — снижает latency для мелких пакетов.
- `connect_timeout` — защита от вечного ожидания.

### 6. `watch`-канал для graceful shutdown

**Решение**: при `Ctrl+C`/`SIGTERM` `shutdown_tx.send(true)`
оповещает accept-loop, который перестаёт принимать новые
соединения. Активные сессии дорабатывают.

**Почему не `CancellationToken`**:
- `watch` входит в `tokio` без дополнительных зависимостей.
- `CancellationToken` из `tokio-util` удобнее, но тащит
  `tokio-util` в зависимости. Для MVP это лишнее.

**Почему не просто `select!` на `ctrl_c`**:
- `ctrl_c` в `accept_loop` заставил бы держать сигнал-хендлер
  внутри каждой задачи. `watch` централизует оповещение.

**Что не сделано**: активные сессии не получают уведомления о
shutdown. Если сессия долгая (большая загрузка), она не
завершится за 5 секунд, и процесс убьётся. Для продакшена нужен
`CancellationToken` с явной отменой в `copy_bidirectional`.

### 7. JSON-логи по умолчанию

**Решение**: `tracing-subscriber` настроен на JSON-формат.

**Почему**:
- **Парсинг.** JSON-логи легко принимает Loki, Elasticsearch,
  Vector.
- **Структура.** Поля можно фильтровать, не занимаясь
  regex-магией.

**Цена**: читать JSON глазами неудобно. Для локальной отладки
можно переопределить через `RUST_LOG` и убрать `.json()` в
`main.rs`. Позже сделаем флаг `--log-format=json|pretty`.

## Точки расширения

### Добавить новый протокол (например, Trojan)

1. Создать `crates/skadi-protocol/src/trojan/` с `parse.rs`,
   `handler.rs`, `config.rs`.
2. В `parse.rs` — чистые функции разбора заголовка.
3. В `handler.rs` — `impl InboundHandler for TrojanHandler`
   (`handshake` → `InboundRequest`).
4. Добавить fuzz-таргет в `fuzz/fuzz_targets/`.
5. В `skadi-server` / `skadi-config` добавить `TrojanConfig` и
   вариант в `Protocol` / `handshake_inbound`.
6. Специальные команды (если есть) — ветка по
   `InboundRequest.command` в `handle_connection`.

Парсер и handler не должны знать про `skadi-server`. Только
через `skadi-core` типы.

### Добавить новый транспорт (например, XHTTP)

1. Создать `crates/skadi-transport/src/xhttp.rs`.
2. Реализовать `impl OutboundTransport` с
   `connect(endpoint) -> Result<Self::Stream>`.
3. Если нужен TLS — обернуть `TcpTransport` в `TlsOutboundTransport`,
   затем в новый транспорт / вариант `OutboundTcpTransport`.

Транспорты **не знают про протоколы**. XHTTP-транспорт может
нести VLESS, Trojan или что угодно.

### TLS inbound (реализовано)

Схема:

```
TcpListener::accept() → TcpStream
          │
          ▼
TlsTransport::accept(TcpStream) → TlsStream   # опционально, [transport.tls]
          │
          ▼
EnabledProtocols::detect(wire byte) → Protocol  # sniff при двух протоколах
          │
          ▼
PrefixedStream (prefix byte)                   # если sniffing
          │
          ▼
handshake_inbound(Protocol) → InboundRequest   # InboundHandler
          │
          ▼
OutboundTransport::connect(target) → upstream  # TCP / TLS / REALITY
```

Handlers принимают generic `S: AsyncRead + AsyncWrite + Unpin`.
SNI-роутинг: `SniCertResolver` в `skadi-transport`, конфиг
`[[transport.tls.certificates]]` + fallback `cert`/`key`.

Интеграционные тесты: `crates/skadi-server/tests/tls_*_e2e.rs`.

### Добавить gRPC API

1. `crates/skadi-api/` с protobuf-схемой и `tonic`.
2. Хранилище пользователей — `Arc<RwLock<HashMap<UserId,
   UserConfig>>>` или `DashMap`.
3. `VlessHandler::handshake` при аутентификации берёт read-lock.
4. API-сервер слушает `127.0.0.1`, требует токен.
5. `handle_client` не меняется.

### Добавить метрики

1. `metrics` + `metrics-exporter-prometheus`.
2. Инкременты в `handle_client` и `copy_bidirectional`.
3. `/metrics` — отдельный HTTP-сервер на `127.0.0.1:9090`.

Метрики не должны содержать PII: только агрегаты, без UUID и IP.

## Что дальше

Порядок работ (обновлено 2026-09-11):

1. **Метрики.** Prometheus + `/healthz` — наблюдаемость в проде.
2. **Устойчивость.** Idle timeout, лимит соединений, нагрузочные тесты.
3. **REALITY.** Через `rustls-reality`, поверх готового TLS inbound.
4. **gRPC API.** Hot reload пользователей для панелей.
5. **VLESS UDP/Mux/flow.** Расширение протокола.
6. **TUN.** Клиентский режим.

TLS inbound и интеграционные e2e-тесты (SOCKS5, VLESS, SNI) — готовы.
